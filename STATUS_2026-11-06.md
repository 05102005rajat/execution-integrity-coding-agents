## 1. One paragraph
Question: when tests fail for a reason that is not a bug in the code (a persistent environment fault), can a coding agent tell, or does it edit correct code? Setup: 8 tiny Python repos, two real faults (`stale_pyc` = leftover unchecked-hash bytecode; `stale_build` = an old `build/lib` copy that `conftest.py` puts first), plus a real-bug control and a clean control, Qwen3.5 2B / 4B / 27B on UCI HPC3, 8 repos x 5 seeds = 40 episodes per cell. Headline: this is not only a small-model problem. The 2B diagnoses almost nothing and breaks correct code; the 4B mostly stops short on the build fault; the 27B resolves 82 to 85 percent with no test regressions but needs 2.2x to 2.8x the steps of a real bug and sometimes rewrites correct code and gives a false explanation. One pre-registered hypothesis (D1) was falsified: agents edit LESS under a fault than under a real bug. This is toy-scale, one model family, and close to prior work (FIXEDBENCH), so no novelty claim.

Notes that are easy to get wrong:
- The 2B has 16 regressions across the two faults (9 pyc + 7 build), not 9. "9" is only the stale_pyc cell.
- "Left failing" (the `diagnosis` label, 4B stale_build at 40 steps = 15) and "tests still failing as the agent left the repo" (the post-hoc end-state measure = 16/40) are two different measures. The end-state one was defined after seeing the data.
- Each `rewrote_source` label (2B build 2, 4B 1, 1, 1) ended with passing tests and is not counted as damage.
- All 6 of the 27B's stale_pyc "edits" were behavior-preserving rewrites that also cleared the cache. In 3 (all matrix) the final message invents a false bug ("zip(*m) does not handle non-square matrices").
- 27B stale_build: 3 runs ended with an empty final message after 26 to 34 steps while still failing (a silent stop, also seen in the 4B). Not analysed.

## 4. What did NOT work and was fixed (be upfront about these)
1. First HPC3 batch was INVALID: the agent's `python` helper lost pytest in the cluster venv. Discarded and rerun (`results/INVALID_first_hpc3_batch_shim_bug/`).
2. The first `stale_pyc` forged a timestamp match and was cleared by any rewrite, so it created false confirmations. Replaced by an unchecked-hash cache (PEP 552) before any result was read.
3. Clean-vs-fault is nearly a tautology (passing tests give no reason to edit), so a real-bug control was added.
4. 15 steps was truncating 70 to 88 percent of faulted runs; the 4B was rerun at 40 steps (removed cause 65 to 88 percent for pyc, 25 to 52 percent for build).
5. Harness crashes: endless-loop edits hung grading, Ollama HTTP 500 on malformed tool calls, a 15-minute stuck model request on the 27B. All now handled and counted, none occurred in the final data.
6. The first idea (fabricated failing test) cannot show that a rerun is insufficient, which is exactly Eric's Oct 27 objection.
